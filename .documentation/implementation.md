# Implementation Roadmap

The source of truth for outstanding work. `backlog.md` is the raw intake buffer for new, untriaged ideas; this file is where they land once they are ordered into phases.

- **One Phase, One Conversation**: phases are sized to be finished in a single session. Do not merge them.
- **Delete On Ship**: when a phase ships, its entry here is **deleted**, not annotated — only the `Already Shipped` row survives. See the Definition of Done in `conventions.md`.
- **No Silent Reordering**: a phase's dependencies are listed with it. Do not start a phase whose dependencies are open.

## Ordering Strategy

- **Bugs First**: defects lead, whichever section they came in under.
- **State Before Style**: the invalid-state hook was a prerequisite for both border geometry and `aria-invalid`, and shipped ahead of them.
- **Docs Last**: API documentation and the `README.md` pass come after the API stops moving.
- **Portal After The Library**: the portal must expose every field option and theme token, so it starts only once those are stable.

- how far back can it be supported? the main consumer (EnerQi) in sibling project is still on Angular 18; is it easier to upgrade EnerQi first?

### Phase 16.5 — Date Range Field

Depends on Phase 16 — the single-value contract ships first.

- **The Calendar Is Not The Problem**: the backlog assumed Pikaday could not do ranges. It renders them — `startRange` / `endRange` options and `is-inrange` / `is-startrange` / `is-endrange` classes. What it does not do is manage range _selection_; that is driven from `onSelect`, or with two instances.
- **The Value Contract Is**: `date-field` is single-valued end to end — `Date | null`, one picker, one masked input with one `unicodeTokenFormat`, arrow-stepping over that one date, and `isFilled`. A range mode means a tuple value, a two-segment mask, parse and format path, per-segment arrow-stepping and clear semantics, and range styling that `_pikaday.scss` does not have.
- **Size It Honestly**: the largest single item on this roadmap. Split it before starting.

#### Requirements

**P2 Shell**

- The portal's own control elements use the library's components, with a distinct and compact theme.
- Link to the public GitHub repository.

**P3 Preview Form**

- Every field is previewed, inside one example form with a funny context.
- Several fields of the same type, so config variations of that type can be demoed side by side.
- Laid out in a grid — not every field at full width.
- Fully functional and fillable.
- A different default theme and token config from the library's, as the starting position.
- Option fields always carry sample options that are `disabled` and `readonly`, so their theming can be demoed.

**P4 Form Values View**

- Expandable and collapsible views of the form values currently entered.

**P5 Field Options Editor**

- Every option of every field is changeable, with the result live in the preview form.

**P6 Theme Editor**

- Every theme token is changeable — colour pickers, sliders — with the result live in the preview form.
- Tokens are grouped into categories (colours, geometry, typography, spacing) so a user finds a baseline fast. The current example form does this already; `theme-options.md` is retired at P10 once the portal supersedes it.
- Light and dark colour themes.
- Several pre-designed themes to select and apply as inspiration and starting points. Make them genuinely different from each other — customizing everything is this library's super-power and the portal should prove it.
- Export the resulting theme by copy-paste, and import it back.
- Fonts are selectable. Open question: bundle open-source fonts or fetch them in the browser.

**P7 Adornment Config**

- Prefixes and suffixes configurable as icons, text or buttons, with the result live in the preview form.
- i18n config is changeable, to demonstrate the date field properly.

**P8 Markup Editor**

- An HTML editor over the preview form: modify it, add and remove fields and configurations, see the result.

**P9 Portal Docs**

- Every theme token and field option documented with examples — inline next to the option and on a separate documentation page.
- **Open Question**: how to demonstrate accessibility. A screen-reader mode showing how the form is read out, as a separate view or a toggle.

**P10 Cutover**

- The demo's example form is removed and the root project hosts the portal instead.
- The portal is the GitHub Pages deploy.
- `conventions.md` and the Definition of Done are updated so future features and fixes reach the portal too.
